# Архитектура

## Общая схема

```
Браузер (HTML, CSS, JavaScript, SVG)
        │  JSON по HTTP
        ▼
Сервер FastAPI (пакет voltplan)
  ├── редактор схемы, совместимый с LineCapacity          этап 1
  ├── обмен файлами .cir                                  этап 1
  ├── расчёт: мост к расчётному ядру (пакет linecapacity) этап 2
  ├── пользователи, проекты, совместная работа (SQLite)   этап 3
  ├── типовые нагрузки, сценарии, варианты, сравнение     этап 3
  └── тарифы, оплата, администрирование, консультант      этап 3
```

Клиент не содержит инженерной логики: он показывает схему, собирает действия
пользователя и отправляет их на сервер. Все правила построения, чтения и записи
файлов, расчёта и сравнения выполняются на сервере — в одном месте и с одними
тестами.

## Пакеты

| Пакет | Назначение | Появляется |
|---|---|---|
| `voltplan` | приложение: сервер, API, клиент | этап 1 |
| `voltplan.scheme`, `voltplan.exchange` | редактор схемы, файлы `.cir`; импорт нагрузок из Excel (`meters.py`), документ Word (`docx.py`) | этап 1, этап 3 |
| `voltplan.calc` | мост к расчётному ядру: результаты, настройки расчёта (`settings.py`), функции меню «Расчёт» (`tools.py`), сценарии (`scenarios.py`), сравнение вариантов и ГОСТ 32144 (`compare.py`), эпюра (`profile.py`), годовые потери (`losses.py`), отчёт DOCX (`document.py`) | этап 2, этап 3 |
| `voltplan.accounts` | хранение и службы сайта: пользователи и вход (`users.py`, `security.py`), проекты, варианты, сценарии (`projects.py`), совместная работа (`collab.py`), справочник типовых нагрузок (`reference.py`), свои марки (`marks.py`), тарифы (`tiers.py`), оплата (`billing.py`), администрирование (`desk.py`), параметры сайта (`options.py`) | этап 3 |
| `voltplan.consultant` | консультант на сайте | этап 3 |
| `voltplan.api` | маршруты API по разделам | этап 1 |
| `linecapacity` | расчётное ядро: модель сети, настройки, графики нагрузки, решатель установившегося режима, тепловой расчёт; с этапа 3 — допустимая мощность (`allowed.py`) и распределение по балансному прибору (`meter.py`) | этап 2 |

`voltplan` обращается к `linecapacity` только через мост `voltplan.calc`:
единая структура схемы преобразуется в модель ядра, результаты ядра — в JSON
для клиента, включая текст отчёта и подписи. Ядро о `voltplan` ничего не
знает и может использоваться отдельно. Устройство ядра описано в документе
«Расчётное ядро».

## Единая структура схемы

Одна и та же JSON-структура используется клиентом, сервером, файлами обмена
и базой данных. Она повторяет состав файла `.cir`, поэтому импорт и экспорт
не теряют ни одного поля.

```json
{
  "transformer": {
    "type_name": "ТМ-250", "label": "T1 КТП-54", "x": 50, "y": 40, "h": 5467,
    "sn_kva": 250, "px_kw": 0.74, "pk_kw": 3.7, "unn_kv": 0.4, "uvn_kv": 10,
    "uk_percent": 4.5, "pbv_step": 0, "pbv_steps": 5, "pbv_percent": 2.5,
    "r_ohm": 0, "x_ohm": 0, "kt": 25
  },
  "lines": [{
    "type_name": "СИП-2 3х50+1х54,6", "label": "Л-1",
    "x": 53, "y": 70, "end_x": 133, "end_y": 70, "vertical": 0,
    "line_type": 0, "phase_mode": 0, "length_m": 30, "canvas_length": 80,
    "r_phase_ohm_per_km": 0.641, "r_neutral_ohm_per_km": 0.641,
    "r_single_phase_ohm_per_km": 0.641, "phase_no": 1,
    "r_phase_ohm": 0, "r_neutral_ohm": 0, "feeder_no": 0
  }],
  "poles": [{
    "label": "1/1", "x": 133, "y": 70, "end_x": 193, "end_y": 70,
    "canvas_length": 60, "branch_count": 1, "current_branch_no": 0,
    "feeder_no": 0
  }],
  "consumers": [{
    "type_text": "мощность по ТУ: 3,5 кВт", "label": "1", "address": "",
    "x": 163, "y": 110, "p_kw": 0.35, "cos_phi": 0.998, "phase_mode": 1,
    "phase_no": 1, "load_type": 0, "annual_kwh": 1293, "category": 0,
    "feeder_no": 0
  }],
  "connection_points": [{
    "x": 193, "y": 70, "active": true, "point_kind": 2, "object_no": 0,
    "branch_no": 0, "feeder_no": 0
  }],
  "outgoing_count": 1,
  "spare": {"lines": [], "poles": [], "consumers": []}
}
```

Объекты в списках идентифицируются номером в списке. Раздел `spare` — резерв
последних удалённых объектов, который влияет на заполнение окон и параметры
новых объектов так же, как в LineCapacity (см. «Построение схемы»); в файл
`.cir` он не пишется.

Сервер описывает структуру моделями pydantic и проверяет каждую присланную
схему и каждый файл:
- надписи — без управляющих символов, только символы Windows-1251 и не
  длиннее 255 знаков;
- числа — конечные;
- размеры — не больше, чем допускает LineCapacity: 1200 ЛЭП, 300 опор,
  600 потребителей, 2400 присоединений, 21 отходящая линия, 100 ответвлений
  у опоры;
- файл `.cir` — не больше 8 МБ.

Сообщения об ошибках — на русском, с названием поля.

## Редактор схемы

Сервер хранит правила построения, клиент — только текущее состояние. Каждое
действие пользователя — запрос «схема + действие», ответ — новая схема.

| Действие | Смысл |
|---|---|
| `new` | новая схема: трансформатор, первая отходящая линия, первая опора |
| `outgoing` | ещё одна отходящая от ТП линия с опорой |
| `span` | пролёт с опорой от конца опоры |
| `branch_line` | ответвление к другой линии с опорой (признак «к одиночной опоре») |
| `branch_consumer` | ответвление к потребителю с потребителем |
| `pole` | промежуточная опора на свободном конце линии |
| `consumer` | потребитель на свободном конце ответвления |
| `add_branch` | добавить ответвление к опоре |
| `update` | изменить параметры объекта |
| `delete` | удалить объект |

Правила каждого действия — размещение, сдвиги, удаление, заполнение окон,
отмена — описаны в документе «Построение схемы». Значения, которыми
заполняются окна, выдаёт сервер (`POST /api/scheme/form`). Ответ на действие
содержит, кроме новой схемы, состояния для отмены; отмену выполняет сервер
(`POST /api/scheme/undo`).

## Расчёт

`POST /api/calc` принимает схему, период (`0` — лето, `1` — зима, `2` — оба) и
признак режима минимальных нагрузок. Сервер проверяет, можно ли считать схему,
передаёт её ядру через мост `voltplan.calc` и возвращает:

| Поле | Содержание |
|---|---|
| `period`, `min_load` | выполненный вид расчёта; `min_load` — был ли посчитан режим минимальных нагрузок |
| `seasons` | числа по сезонам: напряжения и мощности потребителей, температуры проводов, шины ТП, трансформатор, наименьшее напряжение, наибольшая температура |
| `labels` | готовые подписи для схемы по сезонам (`"0"`, `"1"`) и для режима минимальных нагрузок (`"2"`); у подписей напряжений и температур признак `bad` — выход за допустимые пределы, по нему клиент окрашивает подпись красным |
| `memo` | строки результатов для окон трансформатора, каждой ЛЭП и каждого потребителя |
| `charts` | графики трансформатора по получасам для каждого сезона: коэффициент загрузки, температура обмоток, температура масла |
| `report` | строки окна «Основные результаты расчётов» с оттенком (заголовок, значение, предупреждение) |
| `good` | заключение о пропускной способности |
| `show_report` | открыть окно отчёта сразу после расчёта: потребителей два и больше |
| `report_ready` | показать отчёт по кнопке «Итоги»: у потребителей больше одной ветви напряжения |
| `min_load_mode` | режим минимальных нагрузок: напряжения всех потребителей, наибольшее напряжение и потребитель; `null`, если режим не считался |

Ответ `409` с текстом причины означает отказ в расчёте: свободный конец ЛЭП,
нет потребителей, нет ЛЭП, ЛЭП нулевой длины, потребитель или опора не
присоединены к ЛЭП, ЛЭП начинается не на опоре, в марке провода нет сечения,
cos φ ≤ 0 у индивидуальной нагрузки (полный список — «Расчётное ядро»).
Величины, вышедшие за пределы вещественных чисел, передаются в JSON как
`null`, а в строках — как `INF`.

Все числа форматирует сервер — так же, как их выводит LineCapacity; клиент
только расставляет готовые строки. Поэтому тексты можно сравнивать с окнами
LineCapacity напрямую.

С этапа 3 запрос расчёта принимает ещё `settings` — изменённые величины
настроек расчёта (настройки проекта и сценария); сервер накладывает их на
справочник типовых нагрузок и проверяет (см. «Расчётное ядро», раздел
«Настройки расчёта»). Размер схемы проверяется по тарифу пользователя.

## API по этапам

| Этап | Маршруты |
|---|---|
| 1 | `GET /api/catalog` — справочник марок; `GET /api/scheme/titles` — названия действий; `POST /api/scheme/menu` — разрешённые действия для точки; `POST /api/scheme/form` — значения окна; `POST /api/scheme/apply` — выполнить действие; `POST /api/scheme/undo` — отмена; `POST /api/exchange/import` — `.cir` → схема; `POST /api/exchange/export` — схема → `.cir` |
| 2 | `POST /api/calc` — расчёт схемы, результаты для схемы и отчёт; `GET /api/catalog/mark` — как понята марка провода (строки окна ЛЭП) |
| 3 | вход: `POST /api/auth/register`, `/login`, `/logout`, `GET /api/auth/state`, `/me`; профиль: `POST /api/account/password`, `/profile`, `GET /api/account/tier`; проекты: `GET/POST /api/projects`, `GET/PATCH/DELETE /api/projects/{id}`, `GET/PUT /api/projects/{id}/scheme`, `POST /api/projects/{id}/variants`, `PATCH/DELETE /api/projects/{id}/variants/{v}`, `GET/PUT /api/projects/{id}/settings`, `GET/POST /api/projects/{id}/scenarios`, `PATCH/DELETE /api/projects/{id}/scenarios/{s}`, `POST /api/projects/{id}/compare`, `GET/POST /api/projects/{id}/shares`, `DELETE /api/projects/{id}/shares/{team}`; совместная работа: `/api/teams`, `/api/teams/{id}/members/{u}`, `/api/invitations`, `/api/friends`, `/api/messages` (с файлом), `/api/messages/{id}/file`, `/api/notifications`, `/api/notifications/seen`; расчёт: `GET /api/calc/settings`, `POST /api/calc/load-kind`, `/api/calc/allowed`, `/api/calc/meter`, `/api/calc/scenarios`, `/api/calc/excel/periods`, `/api/calc/excel/apply`, `/api/calc/profile`, `/api/calc/losses`, `/api/calc/report.docx`; свои марки: `GET/POST /api/marks`, `DELETE /api/marks/{id}`; тарифы и оплата: `GET /api/tiers`, `POST /api/billing/checkout`, `/api/billing/confirm`, `GET /api/billing/poll/{id}`, `/api/billing/history`; состояние: `GET /api/health` (без входа); администрирование: `/api/admin/users`, `/api/admin/users/{id}/tier`, `/api/admin/users/{id}/admin`, `/api/admin/journal`, `/api/admin/broadcast`, `/api/admin/payments`, `/api/admin/reference`, `/api/admin/options`; консультант: `GET/POST /api/consultant` |

Все маршруты этапов 1–3, кроме входа, регистрации, выхода, `GET /api/auth/state`,
`GET /api/tiers` и `GET /api/health`, требуют входа: без него ответ `401` «Войдите в
систему». Закрытые страницы по имени файла (`/app.html`, `/account.html`,
`/collab.html`, `/pay.html`, `/admin.html`) перенаправляются на `/app`, `/account` и
т. д., где действует та же проверка входа. Переполнение при расчёте
(крайние значения) даёт `409` «Расчёт невозможен…», а не ошибку сервера.
Отказы служб сайта приходят с кодом и понятным текстом: `400` — неверные
данные, `403` — нет права или функция не входит в тариф, `404` — объекта нет
или он чужой, `409` — конфликт (повторное приглашение, закрытый счёт), `402` —
банк отклонил оплату, `429` — слишком много попыток входа или вопросов
консультанту, `503` — консультант недоступен.

## Хранение данных (этап 3)

Две базы SQLite в каталоге данных сервера (`site_data`, переменная
`VOLTPLAN_DATA`):

- `credentials.db` — только учётные данные: почта, соль и хэш пароля
  (PBKDF2-HMAC-SHA256, 200 000 повторений);
- `voltplan.db` — всё остальное:

| Таблица | Содержание |
|---|---|
| `profiles` | имя, тариф и срок его действия, признак администратора, язык, метка сеанса, время регистрации и входа |
| `attempts` | неудачные попытки входа: после пяти подряд — пауза 5 минут |
| `projects`, `variants` | проекты (владелец, название, архив, настройки расчёта) и варианты схемы; схема — JSON единой структуры, пустой вариант — пустая строка |
| `scenarios` | сценарии проекта: название, изменённые настройки, период, режим минимальных нагрузок |
| `teams`, `team_members`, `project_shares` | команды, роли (владелец, редактор, читатель), проекты, открытые командам |
| `invitations`, `friends` | приглашения в друзья и в команды, дружба |
| `messages` | переписка: личная и командная; файл — имя в базе, содержимое в каталоге `files` |
| `notifications` | уведомления с отметкой о прочтении |
| `reference_settings` | изменённые администратором величины справочника типовых нагрузок |
| `own_marks` | свои марки ЛЭП и трансформаторов |
| `payments` | счета: тариф, сумма в центах, способ, состояние, маска карты, ссылка платёжного сервиса |
| `site_options` | параметры сайта: стоимость электроэнергии |
| `consultant_questions` | время и длина вопросов консультанту — для ограничения частоты |
| `audit` | журнал действий |
| `revoked_sessions` | подписи токенов, отозванных при выходе, со сроком хранения |

**Сеанс.** После входа сервер ставит cookie `voltplan_session` (HttpOnly,
SameSite=Lax, 7 дней) с токеном: номер пользователя, метка сеанса и срок,
подписанные HMAC-SHA256 ключом сервера (`secret.key` в каталоге данных или
переменная `VOLTPLAN_SECRET`) и снабжённые случайной частью. Смена пароля
меняет метку — старые токены перестают действовать. Выход отзывает именно этот
токен: его подпись заносится в `revoked_sessions`, и скопированная cookie больше
не принимается; другие сеансы пользователя продолжают работать.

**Права на проект.** Владелец — всё; проект, открытый команде: участник с
ролью «редактор» (и владелец команды) сохраняет схему, варианты, настройки и
сценарии; «читатель» только открывает и считает. Чужой проект без доступа —
`404`, действие без права — `403`.

**Тарифы.** «Демо» (бесплатно), «Профессионал» ($19 за 30 дней), «Максимум»
($39) различаются пределами (проекты, варианты, варианты в сравнении,
сценарии, опоры и потребители в схеме) и функциями (свои марки и DOCX — с
«Профессионала», эпюра, годовые потери и создание команд — в «Максимуме»).
Истёкший тариф считается «Демо». Пределы проверяет сервер (`accounts/tiers.py`):
число действующих проектов — при создании и при возврате проекта из архива;
размер схемы — при расчёте, во всех функциях меню «Расчёт» и при сохранении в
проект. Открыть и сохранить файл `.cir` можно при любом размере схемы, который
допускает формат.

**Оплата.** Два способа: демонстрационная форма карты (проверка номера по
алгоритму Луна, срока, CVV; номер 4000 0000 0000 0002 даёт отказ банка) и
тестовая среда bePaid: сервер создаёт счёт на странице bePaid (`test: true`),
покупатель возвращается на `/pay?await=…`, состояние узнаётся опросом.
Если тестовая среда недоступна, счёт переводится на демонстрационную форму.
Полный номер карты нигде не хранится — только маска. Оплата продлевает тариф
на 30 дней от конца текущего срока того же тарифа. Счёт зачисляется один раз:
перевод счёта из «ожидает оплаты» в «оплачен» и продление тарифа выполняются в одной
транзакции, повторное подтверждение того же счёта ничего не меняет. Пока действует
старший тариф, младший не оплачивается (`409`), чтобы оплаченные дни не пропали.
Если счёт на младший тариф был открыт раньше и оплачен уже при действующем
старшем, деньги зачитываются в старший: его срок продлевается на 30 дней × цена
младшего / цена старшего (за «Профессионал» при «Максимуме» — на 15 дней), об этом
приходит уведомление. При переходе на старший тариф оставшиеся дни младшего
не пропадают: срок старшего — 30 дней плюс остаток × цена младшего / цена
старшего. Тариф, выданный администратором без срока, не продаётся повторно
(`409`, «без срока»); если старый счёт оплачен уже при таком тарифе, тариф
не меняется, а в платеже записано пояснение. Ни один путь к странице или файлу
не даёт ошибки сервера: имя закрытой страницы приводится к одному виду (без
учёта регистра, конечных косой черты, точек и пробелов, части после двоеточия),
путь, который нельзя открыть как файл, отвечает `404`.

**Вложения в переписке.** До 5 МБ. Отклоняются исполняемые файлы: по расширению
(после отбрасывания конечных точек и пробелов в имени) — `.exe`, `.bat`, `.cmd`,
`.com`, `.msi`, `.ps1`, `.vbs`, `.js`, `.hta`, `.lnk`, `.cpl`, `.wsf`, `.scr`,
`.dll` и другие, и по содержимому — файлы, начинающиеся с сигнатуры исполняемого
файла Windows (`MZ`), Linux (`ELF`) или сценария (`#!`).

## Клиент

Страницы и модули JavaScript без сборщика (модули ES). Холст — SVG: слой линий,
слой опор, слой потребителей, слой подписей, слой результатов, слой точек
присоединения. Масштаб и сдвиг — преобразованием корневой группы.

| Этап | Модули клиента |
|---|---|
| 1 | `api.js`, `dom.js`, `state.js`, `render.js`, `canvas.js`, `actions.js`, `forms.js`, `picker.js`, `dialogs.js`, `props.js`, `exchange.js`, `main.js` |
| 2 | `calc.js` — окно запуска расчёта; `results.js` — подписи на схеме, отчёт, результаты в окнах; `charts.js` — графики трансформатора |
| 3 | `session.js` — сеанс, шапка редактора, уведомления, тема; `i18n.js` — языки; `language.js` — переключатель RU · EN · 中文; `project.js` — проекты и варианты в редакторе; `tools.js` — меню «Расчёт»: присвоение нагрузок, балансный прибор, импорт из Excel, настройки, сценарии; `analysis.js` — сравнение вариантов, эпюра, годовые потери, отчёт DOCX; `consultant.js` — панель консультанта; `site.js` — общая шапка сайта, тема, появление разделов, счётчики, наклон карточек; `panel.js` — окна и списки кабинета; `scenes.js` — анимированные сцены страниц (холст 2D), `hero3d.js` — объёмная сцена сети на главной; страницы: `home.js`, `page.js`, `status.js`, `auth.js`, `account.js`, `collab.js`, `tariffs.js`, `pay.js`, `admin.js` |

Страницы этапа 3: `/` — главная, `/features`, `/about`, `/faq`, `/status`,
`/tariffs`, `/login`, `/register` — открытые; `/app` — редактор, `/account` —
личный кабинет, `/collab` — совместная работа, `/pay` — оплата, `/admin` —
администрирование — только после входа (иначе переход на `/login?next=…`).

Стили: `site.css` — страницы сайта (шапка, разделы, карточки, тарифы, формы,
кабинет, совместная работа, оплата); `admin.css` — панель администратора;
`base.css` и `app.css` — редактор (тёмная панель инструментов, холст,
панели, окна); `consult.css` — панель консультанта. Цвета заданы
переменными; тёмная тема переопределяет переменные. Сцены на холсте берут цвета
из тех же переменных и свои короткие подписи — из словаря внутри `scenes.js`
на трёх языках. Снимки редактора для страниц сайта лежат в `web/shots`.

**Языки.** Словари `web/i18n/en.json` и `web/i18n/zh.json`: ключ — русский
текст, значение — перевод; строки с числами и именами записаны шаблонами
(`Значение минимального напряжения: {p1} В`). После загрузки страницы и при
каждом изменении её содержимого `i18n.js` переводит видимый русский текст и
подсказки. Пользовательские данные (названия проектов, имена, сообщения,
надписи на схеме) помечены `translate="no"` и не переводятся. Полноту словарей
проверяет тест: он собирает все русские строки страниц, модулей клиента и
сервера (включая шаблоны f-строк) и требует перевода каждой.

## Запуск

```
python -m voltplan
```

Сервер слушает `http://127.0.0.1:8000`. Зависимости перечислены в
`pyproject.toml`: FastAPI, uvicorn, pydantic, python-multipart; с этапа 2 —
NumPy и SciPy для расчётного ядра; с этапа 3 — openpyxl для чтения книг Excel.

| Настройка | Назначение |
|---|---|
| `VOLTPLAN_DATA` | каталог данных (по умолчанию `site_data` рядом с проектом) |
| `VOLTPLAN_SECRET` | ключ подписи сеансов (иначе создаётся `secret.key`) |
| `VOLTPLAN_CONSULTANT_KEY` или файл `consultant.key` | ключ доступа консультанта |
| `VOLTPLAN_BEPAID_SHOP`, `VOLTPLAN_BEPAID_KEY` или файл `bepaid.key` | свой тестовый магазин bePaid (иначе — открытый тестовый магазин bePaid) |
| `python -m voltplan --make-admin почта` | выдать права администратора зарегистрированному пользователю |
